# **System Quality & Code Architecture Guidelines (.docs/quality.md)**

Данный документ устанавливает жесткие инженерные стандарты, метрики стабильности и требования к качеству кода для проекта **Levitating AI Assistant v1.0**. Вдохновляясь бескомпромиссным подходом к качеству компонентов и общей надежности, свойственным лучшим образцам японского автомобилестроения, а также строгими практиками промышленного IT, эта спецификация призвана исключить компромиссные решения (костыли) на всех уровнях архитектуры.

## **1\. Философия надежности и архитектурные принципы**

> * **Hardware-First для критических путей:** Программный код никогда не должен компенсировать аппаратные недоработки. Если возможна реализация функции на аппаратном уровне (например, генерация ШИМ, подтяжка шины, фильтрация питания), она должна быть выполнена в кремнии, а не в коде.  
> * **Нулевая терпимость к джиттеру (Zero-Jitter Tolerance):** Управление левитацией (фазовый сдвиг) не терпит прерываний. Любой код, блокирующий исполнение главного цикла (Core Loop) сопроцессора более чем на 1 микросекунду, считается бракованным.  
> * **Изоляция отказов (Fault Isolation):** Падение одного модуля (например, отвал Wi-Fi на ESP32) не должно приводить к краху системы. Левитационный контур (RPi 5 \+ RP2040) обязан уметь безопасно приземлить Агента даже при полной потере связи с ним.

## **2\. Стандарты написания кода (Code Guidelines)**

| Стек / Среда | Обязательные паттерны и ограничения   |
| :---- | :---- |
| **C/C++ (RP2040 & ESP32)** | **Никаких blocking delays:** Использование delay() строго запрещено. Вся логика строится на конечных автоматах (State Machines) и аппаратных таймерах (millis() / micros()). **Отсутствие динамической памяти:** Запрещено использование malloc(), new и класса String в основном цикле для предотвращения фрагментации кучи (Heap Fragmentation). Использовать статические буферы и char массивы. **Сторожевые таймеры:** Обязательная реализация I2C Watchdog и Hardware Watchdog (WDT) на случай зависания от ЭМИ-наводок. |
| **Python 3 (Raspberry Pi 5\)** | **Асинхронность:** Весь I/O (сеть, чтение SPI/I2C) реализуется через asyncio. Главный цикл ПИД-регулятора не должен ждать ответа от LLM. **Строгая типизация:** Обязательное использование Type Hints (-\> float, Dict\[str, Any\]) для работы статических анализаторов (mypy). **Обработка исключений:** Обертывание вызовов сенсоров в try...except с обязательным логированием сбоев и переходом в Safe Mode. |

## **3\. Метрики стабильности и качества (QoS)**

ИИ-агент при написании и профилировании кода должен ориентироваться на следующие целевые показатели:

> 1. **Частота ПИД-контура (Control Loop Rate):** Цикл "Опрос Холлов \-\> ПИД \-\> Пакет на RP2040" должен стабильно выполняться с частотой **≥ 800 Гц**.  
> 2. **Latancy связи (SPI/UART):** Время отклика сопроцессора RP2040 на команду изменения скважности не должно превышать **1 мс**.  
> 3. **Thermal Throttling:** Программный алгоритм Smooth Ramp-Up обязан гарантировать, что скважность ШИМ на 8-вольтовой линии никогда не превысит установленный лимит (например, 50%), чтобы избежать деградации компонентов и срабатывания термозащиты адаптера.

## **4\. Практики тестирования и CI/CD**

> * **TDD (Test-Driven Development) для математики:** Любая функция (матрицы вращения Gimbal, Sensor Fusion, ПИД) сначала покрывается модульным тестом, в который подаются синтетические (mock) данные. Только после прохождения теста код допускается к прошивке на плату.  
> * **Boundary Testing (Тестирование граничных условий):** Агент обязан писать тесты, проверяющие поведение системы при экстремальных значениях (например, ToF выдает 0 мм, АЦП выдает мусор или float NaN). Код должен корректно отбрасывать такие пакеты.  
> * **Dry-Run Mode:** Наличие режима "сухого прогона", при котором математика и логика на RPi 5 работают в полном объеме, но итоговая команда включения силовых ключей игнорируется. Используется для безопасной отладки LLM-интеграций.
